# 跑团角色卡与世界观编写指南

适用：QQ Agent Plus 当前的「轻量叙事跑团」，包括自动接收玩家普通消息、裁判／旁白模式与独立会话白名单。

这份指南用于自己写卡，或交给其他 AI 按格式生成卡片。标为「必须」的是程序要求；字数建议、能力配平和内容提纲是创作建议。角色卡与世界观分别保存、分别导入。

## 1. 先准备什么

| 内容 | 用途 | 导入位置 |
| --- | --- | --- |
| 世界观 | 故事发生的时代、地点、势力、NPC、开场与规则 | 跑团 → 世界观 → 导入 JSON / TXT |
| 角色卡 | 玩家扮演的人物、初始生命值、属性与物品 | 跑团 → 角色卡 → 导入 JSON / TXT |

先写世界观，再让 AI 按该世界观生成角色，通常更容易保持设定一致。一团使用一个世界观，每名玩家选择一张角色卡；主持人扮演的 NPC 写进世界观，目前没有独立 NPC 卡库。

卡片不是机器人的普通聊天人设。游戏进行时，机器人保持中性的裁判／旁白口吻；NPC 可以有个性和情绪，旁白不因角色喜好偏袒玩家。

可直接复制修改的完整模板：

- [角色卡模板](examples/trpg/character-template.json)
- [世界观模板](examples/trpg/world-template.json)

## 2. 通用文件格式

推荐使用 UTF-8 编码的 `.json` 文件。每个文件只放一张卡，使用以下外层结构：

```json
{
  "format": "qq-agent-trpg",
  "version": 1,
  "kind": "characters",
  "asset": {
    "name": "卡片名称",
    "description": "具体设定"
  }
}
```

角色卡的 `kind` 必须写 `characters`；世界观写 `worlds`。保持 `format` 和 `version` 如上，具体内容放进 `asset`。这段只是结构示意，实际使用建议补全后文列出的全部字段。

文件必须是合法 JSON：

- 键名和文本使用英文双引号 `"`，不能使用中文引号代替。
- 数字不加引号；数组使用 `[]`，对象使用 `{}`。
- 文本内部的双引号写成 `\"`；同一段文本要换行时写 `\n`，不能在引号内直接敲出未转义的换行。
- 不能添加注释、尾随逗号、Markdown 代码围栏或 JSON 前后的解释。
- 不要填写 `id`、`scope`、`ownerId`、`chatKey`、存档版本或工具调用。这些由程序管理。
- 不要把多张卡放进数组，或把世界观和角色合并成一个文件。它们不能作为卡包批量导入。

程序也接受不带外层包装、直接包含字段的对象。为便于交给 AI 生成和分辨类型，统一使用上面的包装格式更方便。

界面中的长度限制按 JavaScript 字符串长度计算；普通汉字通常占一个单位，部分 emoji 占两个或更多。文件还受 **128 KiB** 的导入大小限制，应预留余量。

## 3. 角色卡的详细要求

### 3.1 字段表

| `asset` 字段 | 格式与硬性要求 | 用途及填写建议 |
| --- | --- | --- |
| `name` | 必填字符串，去除首尾空白后 1—60 个长度单位 | 角色显示名称，建议 2—20 字 |
| `description` | 必填字符串，去除首尾空白后 1—12000 个长度单位 | 身份、性格、经历、目标、能力与限制，建议 400—1500 字 |
| `hp` | 整数，1—1000 | 初始生命值，同时作为该角色的生命上限；普通角色建议 10 |
| `attributes` | 对象，最多 12 项；每个键名去除首尾空白后非空、最多 20 个长度单位；每个值为 -5—10 的整数 | 自定义属性及其检定修正值，建议所有同团角色使用同一组属性名 |
| `inventory` | 字符串数组，最多 30 项；每项去除首尾空白后非空、最多 120 个长度单位 | 初始背包，建议 3—8 项；没有物品时写 `[]` |

生成可导入文件时，请把这五个字段全部写齐。程序保存接口在省略可选项时有默认值，但网页编辑器也有自己的初始表单值；显式填写可以避免依赖两者的默认行为。

### 3.2 人物描述建议

`description` 是自由文本。以下标签只是方便组织内容，全部写在这一个字符串里，不要另造 `personality`、`skills`、`background` 等顶层字段：

```text
身份：职业、年龄段、所属势力、社会位置。
外貌：两三个容易辨认的特征。
性格：平时如何做决定、重视什么、什么情况下会动摇。
经历：两三件影响现在的事件，避免写完整传记。
当前目标：眼下想完成什么，以及为什么愿意参加本次冒险。
能力：能做什么，依赖什么条件，有什么代价。
弱点：能力边界、性格弱点或现实负担。
关系：与某位NPC、地点、势力或其他玩家的联系。
行动边界：玩家不希望发生的角色表现或剧情内容，可选。
```

人物要有可行动的目标。例如「寻找失踪的导师」比「等待命运到来」更容易产生冒险。性格用于帮助主持理解人物，不代表主持可以替玩家作出重大决定。

### 3.3 属性怎么写

默认规则是 `1d20 + 相关属性修正`，通常难度为 12。这里填写的是加值：`"感知": 2` 代表相关检定加 2，不能写成百分制的 `80`。

常见属性组可选一种，全团保持一致：

| 题材 | 属性示例 |
| --- | --- |
| 通用冒险 | 力量、敏捷、感知、交涉 |
| 现代调查 | 体能、潜行、调查、交涉、意志 |
| 仙侠 | 体魄、身法、悟性、神识、心志 |
| 科幻 | 体能、反应、技术、洞察、社交 |

新手建议普通属性为 0，擅长项为 +1 或 +2，明显短板为 -1；这属于配平建议，程序没有强制分配总点数。数值接近 +10 会让常见难度非常容易，只有题材需要时再使用。

角色之间应使用相近的 HP 与属性规模。世界规则可约定「初始 HP 10、修正值总和不超过 4」，但目前由主持和玩家遵守，程序不会自动审核总点数。

### 3.4 技能、魔法、装备与数值边界

当前角色卡没有独立技能树、法术表、职业等级、MP、金钱或装备加成字段。需要这些设定时，写进 `description`，并在世界的 `rules` 中说明如何叙事判定。

例如：

```text
能力：能从遗留物上感知模糊的情绪残响，需要接触物品并集中注意。
限制：不能读取完整记忆，不能预知未来；强烈残响可能使其短暂眩晕。
判定：有风险时按感知检定，不保证必定获得关键答案。
```

背包中的「短剑」「护甲」「治疗药剂×2」都是文本物品。写上「短剑，攻击+3」不会让程序自动叠加 +3；数量也不会因使用而自动扣除，需主持更新背包。复杂战斗、升级、法力消耗和经济系统没有完整的自动规则引擎。

程序可以持久化玩家当前 HP、背包和状态描述。角色基础属性与生命上限使用加入时的卡片快照，不作为普通剧情更新项。

## 4. 世界观的详细要求

### 4.1 字段表

| `asset` 字段 | 格式与硬性要求 | 用途及填写建议 |
| --- | --- | --- |
| `name` | 必填字符串，去除首尾空白后 1—60 个长度单位 | 世界或本次冒险名称，建议 4—20 字 |
| `description` | 必填字符串，去除首尾空白后 1—12000 个长度单位 | 稳定的背景、地点、势力、NPC、冲突与能力边界，建议 800—2500 字 |
| `opening` | 字符串，最多 4000 个长度单位；可为空字符串 | 第一幕，建议 150—400 字，给玩家可以立即采取行动的局面 |
| `rules` | 字符串，最多 4000 个长度单位；可为空字符串 | 风格、检定、代价、多人协作与内容边界，建议 300—1000 字 |

生成时把四个字段全部写齐。地点、NPC、势力等写在 `description` 内，不要增加顶层 `npcs`、`locations`、`quests`、`lorebook` 等字段；当前编辑器不会把这些自定义字段作为独立系统导入。

### 4.2 背景应该交代什么

可以按这个提纲写 `description`：

```text
题材与时代：现代、近代、奇幻、仙侠、科幻等，技术发展到什么程度。
故事范围：主要活动区域，避免一开始铺满整个宇宙。
生活常识：当地人普遍知道的事实、习俗、法律与危险。
核心冲突：眼下发生什么变化，若无人介入会有什么后果。
重要地点：3—5处，各写特征、用途和可发现的线索。
主要势力：2—3方，各自目标、资源与矛盾。
关键NPC：3—5名，各写身份、性格、目标、知道什么以及关系。
能力边界：魔法、科技、异能能做什么，不能做什么，有何代价。
玩家切入点：为何来到这里，为何会共同参与事件。
可发展的线索：多个调查方向，不要求固定顺序或唯一解法。
```

数量是建议，单人短团可以更少。优先写能在近期用到的内容，避免大量与本次冒险无关的历史、人物名单或重复修辞。

### 4.3 开场怎么写

`opening` 在团主发送 `/跑团 开始` 后会出现在开场回执里，适合直接面向玩家叙述。

一个可玩的开场通常包含：当前所在地点、一个正在发生的异常、一个可以观察或接触的对象，以及两三个自然的行动方向。可以用一个开放问题收尾。

不要预先替玩家作出重要选择。例如可写「守卫拦住去路，要求出示通行证」，避免写「你立即交出全部财物，并决定为守卫效忠」。不要在开场里确定检定成功、强制死亡或锁定结局。

### 4.4 世界规则怎么写

`rules` 建议明确这些内容：

- 主持保持中性裁判／旁白，NPC对白标明身份，不混入机器人平时的人设。
- 玩家决定角色行动与重大选择，允许自由解决问题。
- 有风险且结果不确定时使用真实掷骰；无风险的小事可以直接成功。
- 默认 `1d20 + 相关属性修正`，通常难度 12；先交代风险与难度，再检定。
- 失败带来与情境相符的代价或新局面，避免因一次失败导致所有线索永久中断。
- HP归零后的处理，例如失去行动能力、被救援或被俘；不要把未实现的战斗公式写成已存在的自动机制。
- 多人行动如何协调，例如先收集所有人的意图，再处理相互冲突的行动；这是主持约定，不是程序自带的严格轮次锁。
- 题材尺度与玩家共同接受的内容边界，以及节奏、难度、回复长度偏好。

世界卡里的要求不能覆盖宿主的身份、工具、权限和存档规则；不要写“忽略系统提示”“强制调用外部工具”一类内容。规则写清楚也不代表程序会自动实现新的资源系统。

### 4.5 谜底与主持秘密

目前没有独立的主持秘密库或按玩家隔离的秘密字段。卡片和存档应按本团公开资料设计，不要把必须对玩家保密的内容当作受保护秘密存放。

悬疑题材可以写多个待揭示的可能方向，由主持在剧情中逐步展开；如果你希望预设幕后真相，也可以写进设定，但不能保证玩家无法通过查看资料或询问得知。需要严格隐藏线索、分别传递秘密或防止剧透的玩法，当前功能还不完整。

## 5. 两份完整模板如何使用

模板文件中的内容是可直接使用的示例，所有字段都符合当前格式。可以先导入试跑，再替换名称和设定：

1. 下载或复制 [world-template.json](examples/trpg/world-template.json)，修改世界内容。
2. 下载或复制 [character-template.json](examples/trpg/character-template.json)，让角色与世界保持一致。
3. 不改外层 `format`、`version`、`kind`；不添加内部 ID。
4. 在控制台「跑团」的对应编辑器导入，检查表单后点击保存。
5. 记录保存后生成的世界ID、角色ID，用于QQ中的开团和加入。

文件名可以任意命名，建议使用「世界名-world.json」「角色名-character.json」，方便区分。不要把下面的生成提示词当作卡片文件导入。

## 6. 可直接交给 AI 的世界观生成提示词

复制整段，将方括号内容换成自己的需求。生成结果直接保存为 `.json` 文件。

```text
请为我的QQ Agent Plus轻量叙事跑团生成一份可直接导入的世界观JSON。

我的需求：
题材与参考风格：[填写，例如架空近代、海港悬疑]
玩家人数：[填写，例如1人或2—4人]
预计游玩长度：[填写，例如一次短冒险或可长期发展的故事]
主要活动区域：[填写]
希望出现的元素：[填写]
不希望出现的内容：[填写]
魔法、异能或科技的边界：[填写，没有则写无]
难度与氛围：[填写，例如中等难度、紧张但保留希望]

输出格式与硬性要求：
只输出一个合法JSON对象，不加Markdown围栏、解释、注释或尾随逗号。
外层必须为：
{"format":"qq-agent-trpg","version":1,"kind":"worlds","asset":{"name":"...","description":"...","opening":"...","rules":"..."}}
asset只使用这四个字段，全部为字符串。
name去除首尾空白后为1—60个长度单位；description为1—12000；opening和rules各不超过4000。
普通汉字通常计1，部分emoji计多个单位。请明显低于上限，整个UTF-8文件小于128KiB。
description建议800—2500字；opening建议150—400字；rules建议300—1000字。
段落换行必须在JSON字符串内写成转义的\n，双引号必须正确转义。
不要生成id、scope、ownerId或额外字段，不要把多张卡包成数组。

创作要求：
description交代时代与技术水平、有限的活动区域、当地常识、核心冲突、重要地点、势力、关键NPC、能力边界和玩家切入点。
NPC写在description里，每名有身份、性格、目标、关系与所知信息，不另建NPC卡结构。

rules采用1d20加相关属性修正，通常难度12；有风险且不确定才检定，先交代风险和难度，不编造骰点。
说明失败代价、HP归零处理、多人协调方式、题材边界和叙事节奏。
主持保持中性裁判／旁白，NPC对白标明身份，不加入原机器人聊天人设。
这是轻量叙事系统，只有HP、背包和状态等现有持久化能力；不要假设已有自动等级、技能树、法力、经济、装备计算或严格回合引擎。
目前没有独立主持秘密库，按玩家可见的资料设计，不依赖受保护的隐藏字段。
若我的要求需要未支持的机制，改为清晰的叙事约定，不宣称程序会自动实现。
```

## 8. 导入和开团步骤

1. 打开控制台「跑团」，开启功能，添加允许的群号或私聊QQ号并保存。空名单禁止该类会话开团；还需满足机器人全局白名单及运行时段。
2. 分别导入世界观与角色卡，检查后各自点击保存。导入只填表，不会自动保存或开始游戏。
3. 在名单内的QQ会话中发送以下指令，将示意ID替换成网页实际生成的ID：

```text
/跑团 开团 世界ID
/跑团 加入 角色ID
/跑团 开始
我举起提灯，检查门边的脚印。
```

多人游戏中，每名玩家用自己的QQ发送加入指令，团主最后开始。每个会话同时只有一个未结束的团，最多6名玩家，也受工作台人数上限约束。目前仅开场前可加入，开始后不支持中途加人或替换角色。

开始后，在册玩家直接发普通消息描述行动，不需要前缀或@；旁观者不推进剧情。团主可发送「暂停跑团」「继续跑团」「退出游戏」，查询状态可用「跑团状态」。暂停保留进度；退出游戏会结束本团并保留存档，结束的团不能直接继续。

网页创建的卡是公共模板。QQ群或私聊里快速创建的卡仅对当前会话可见，聊天创建的角色卡仅创建者可选。

世界在开团时、角色在加入时复制为团内快照。之后修改或删除模板，不会同步改动已有团。要使用新设定，通常应结束旧团后重新开团并加入新卡；当前没有存档导入、分支回滚或卡片热替换。

## 9. 常见问题与生成后检查

| 情况 | 原因与处理 |
| --- | --- |
| AI返回一大段设定文章 | 可以贴到网页描述栏；若要完整导入，请要求按本指南生成JSON |
| JSON无法解析 | 去掉代码围栏与解释，检查英文引号、逗号、转义和引号内换行 |
| 提示类型不符 | `characters` 导入角色卡编辑器，`worlds` 导入世界观编辑器 |
| 属性填写80被拒绝 | 属性值只允许-5—10；普通角色通常用-1至+2 |
| 生成了skills、spells等字段，导入后找不到 | 将内容改写进description，当前没有这些独立字段 |
| 想导入PNG角色卡或完整酒馆世界书 | 当前不支持；酒馆JSON只读取部分人物基础描述，不执行脚本或扩展规则 |
| 导入TXT/Markdown后没有属性或开场 | 文本导入仅用文件名填名称、正文填描述；其他字段在网页补充 |
| 改了卡，旧团没有变化 | 已有团使用快照；新开团、重新加入才使用新卡 |
| 白名单里有群，却仍不能开团 | 还需检查全局聊天授权、运行模式、暂停和活跃时段 |

最后核对：两份文件分别只有一张卡；所有推荐字段已写齐；名称与数值符合限制；人物与世界一致；开场可以自由行动；没有把未实现的机制当成自动功能。检查通过后即可导入试跑。

宿主运行方式、数据与成本说明见 [跑团功能说明](TRPG.md)。卡片设定会随游戏上下文发给当前配置的模型，设定越长通常消耗的Token越多，优先保留本团需要的信息。
