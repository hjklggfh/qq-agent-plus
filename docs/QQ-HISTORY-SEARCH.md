# 按关键词检索QQ原始历史

模型工具 `search_chat_history` 用于确认以前具体聊过什么、当时最后采用了什么方案。
它会实际调用QQ协议端的历史接口，并查询agent已保存的原始消息；不查询人物印象或会话摘要来冒充原文。

可以直接问：

- “查一下上周关于服务器部署的聊天，当时最终采用了什么方案？”
- “在这个群的历史里搜‘域名’，看看之前是怎么配置的。”
- “查2026-10-01到2026-10-10关于备份的记录。”

模型会根据关键词、日期获取消息，并取少量附近原文辅助理解。结果包含原QQ消息ID、时间、发送者、
正文节选和来源：`qq-history-api` 是QQ/SnowLuma历史接口返回的消息，`agent-archive` 是agent保存的原文。
不会把“没有搜到”解释成“从未聊过”，也不能凭印象补造最终结论。

## 当前协议能力与范围

线上已核对SnowLuma 1.14.15-node。[官方群历史接口](https://snowluma.github.io/zh/docs/api/extended/get_group_msg_history)
与[好友历史接口](https://snowluma.github.io/zh/docs/api/extended/get_friend_msg_history)支持消息锚点、条数和翻页方向。
本版动作目录没有QQ客户端式的全库关键词搜索动作，因此这里采用“历史分页读取→关键词筛选”，
不能声称已接入QQ原生全库搜索。群历史接口可能回退到协议端缓存，不能把接口成功当成云端完整历史证明。

- 每次最多4页，每页请求50条；每轮最多2次、合计8页。18秒总期限，每个请求最多10秒，保持串行。
- 返回最多6个匹配片段及少量5分钟内的附近原文，合计最多8条；输出通常最多2400字符，随已有省Token设置收紧，硬边界800–3000字符。
- 返回 `coverage`：实际页数、读取条数、时间范围、停止原因及 `nextCursor`。需要继续时传入 `beforeMessageId`；负数消息ID必须保留负号。
- 查询过去日期时，优先用该日期内已知的QQ消息ID定位；锚点过期时回退最新页，并明确报告范围。
- 当前窗口的agent存档按关键词查询全部保留时间，最多取200条候选；不受跨窗口30/90天窗口限制。
  QQ能返回多久由账号权限、服务端及协议端保留记录决定。大群多年的历史无法靠一次有限分页保证查全。
- 只读取机器人账号可访问的会话；无法读取另一个QQ账号手机上独有的记录。不会操作QQ客户端的搜索框，
  不读取加密密钥、不改协议端、不批量全量同步历史，也不下载图片、文件或展开转发卡片。

## 隐私与保存

默认搜索当前窗口；即使关闭跨窗口回忆，当前窗口原始历史仍可按需查询。
显式传其他 `chatKey` 时，必须符合现有白名单、全局/逐窗口隐私、来源限制、回看天数和屏蔽名单，
并且只取本轮实际说话者的消息及可确认归属的机器人回复。跨窗口检索会标记来源，防止改存成当前窗口印象。

引擎的游戏秘密事件不进入结果；对没有本地安全来源记录的私聊机器人发言，采取保守过滤。
已排除的本地片段同样不返回。读取期间权限变化或取消会中止返回，跨窗口消息ID不能在当前窗口引用。

读取不会触发旧消息重放、模型批量整理或QQ测试发送。精简结果随原工具调用留档，
`session.historySearches` 只记查询、覆盖范围、返回数和字符数，不另建完整历史副本。
QQ/SnowLuma自身可能缓存其读取结果，属于协议端原有行为。

实现：`src/memory/chat-history-search.js`、`ChatStore.searchHistoryMessages()`、`historyDateAnchor()`。
测试：`test/chat-history-search.test.mjs`；提示词与工具调度分类也有回归覆盖。
