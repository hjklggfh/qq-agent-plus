# PID 搜索（Agent 内置功能）

PID 是 Pixiv 作品号。本功能在“设置 → PID 搜索”管理，不再安装、启用或审批 Pixiv 插件；关键词取图与指定 PID 复用同一套分级、下载、压缩及发送流程。

## 使用

- `PID 12345678`：从第一页取作品。也支持 `pid`、`Pixiv`、`P站`、`查PID` 前缀。
- 单独发送完整 `https://www.pixiv.net/artworks/12345678`：取该作品。
- `PID 12345678 21-40`：只取第21至40页，页码从1开始。
- `PID 12345678 21`：从第21页开始，最多取设置中规定的页数。
- “来张初音ミク的图”等自然语言仍由聊天模型调用 `pixiv_image`。明确 PID 和完整链接由宿主处理，不消耗聊天模型 Token。普通纯数字不当作指令。

仍受宿主群聊、私聊白名单、运行模式、暂停、时间规则约束。跑团接管会话时优先走跑团，不抢夺游戏消息。重复 QQ 消息事件只处理一次。

## 分级

默认只允许全年龄（safe），另有 R18、R18G。设置页点击“添加群聊／私聊覆盖”，选择会话类型、填写号码并勾选分级即可，不需要编辑JSON。会话覆盖优先于全局默认；配置文件中的对应格式示例：

```json
{
  "group:123456789": ["safe"],
  "private:123456789": ["safe", "r18"]
}
```

删掉该会话条目则恢复默认；保存立即生效，不用重启。主人在QQ中要求修改本会话分级时，可由 `pixiv_set_rating` 工具处理；只有宿主“全局管理员 QQ”能修改，其他人只能查询。控制台可编辑全部会话覆盖。

指定 PID 优先使用已有可信缓存；配置自选代理或作品详情接口时再读取详情，使用有效 `xRestrict`/`x_restrict`，成人标签只会提高限制档位。无代理、无详情接口时不尝试官方直连，也不白等超时。接口缺少分级、返回空值或非法值时，不再默认判断为全年龄；`sl` 也不当作作品内容分级。已获取的可信作品信息在本地缓存24小时，关键词搜索取得的分级也能用于后续 PID 直取。

杭州当前无法直连 Pixiv 官方作品详情接口，旧关键词接口也不支持可靠的 PID 精确查询。因此保留以下明确选择：

1. 默认“拒绝发送”：提示无法确认分级，图片不发出。
2. 在设置页“核实作品分级”中输入 PID，并在确认作品内容后标为 safe/R18/R18G。人工标记只作用于该作品，仍受会话分级过滤；可单独清除。
3. 旧行为兼容选项：仅在当前会话同时明确允许 R18 和 R18G 时发送未知分级作品，消息标明“未知分级”，不会声称它是全年龄。旧插件迁移时保留这项兼容策略，新实例默认拒绝。
4. 可以自行填可用的作品详情接口，模板须含 `{pid}`，或使用已有的自选 HTTP 代理。Cookie 仅发给 Pixiv 官方域名，不发给图片反代或其他详情接口。

**本功能不复用以图搜图的东京中转、隧道、令牌或服务。**默认使用国内图片链路；用户明确授权后可安装独立的 [PID 东京链路](PIXIV_TOKYO.md)，通过本功能自己的 `proxyUrl` 启用。不假定第三方服务长期可用。

可选公开详情模板：`https://pixiv.yuki.sh/api/illust?id={pid}`（[服务文档](https://pixiv.yuki.sh/docs)）。适配其 `success/data` 返回格式，详情里的 `/image/` 图片地址转换为现有 `i.pixiv.re` 完整路径下载，不调用需要 Key 的 Yuki 图片反代。它可以绕开 `pixiv.re/PID.png` 简写查询失败的情况，但不保证每件作品都可用。缺少明确分级或总页数时仍按未知处理，不能根据标题、普通标签或“可访问”推断全年龄。人工标记分级也不会跳过已配置的详情查询，避免丢失真实图片路径。

## 多页与失败处理

### PDF 文件发送

发送 `PID 12345678 PDF`，会把本次可取得的作品图片按原始页码顺序合成一个 PDF，在群聊上传为群文件，在私聊发送文件。`PID 12345678 21-40 PDF` 只打包指定范围；完整 Pixiv 作品链接末尾也可加 ` PDF`。这些明确指令不调用聊天模型。

“设置 → PID 搜索 → 默认发送方式”可选 PDF，保存后普通 `PID 作品号` 就按 PDF 发送；末尾加“图片”临时改回原来的卡片。为保留已有使用习惯，升级后默认仍是图片卡片。

PDF 使用独立页数上限，默认500页，可设1—1000页，不受原来20页/100页卡片上限及每批图片大小限制。下载图片总量与最终 PDF 各限256MB（可设1—512MB），同时仍受单张下载上限、任务超时、分级和宿主会话权限限制。大作品超时可分段请求，任务时间可调至600秒。未配置独立代理时，单页下载沿用 pixiv.re / i.pixiv.re 等现有链路。

复用 JM 的 Python 3 + Pillow 环境与逐页 PDF 写入器，两个功能共用串行处理队列以降低内存峰值；Pixiv 不执行 JM 图片还原。可在 JM 设置中填写已有 Python 路径，不要求开启 JM。图片先落盘，再逐页解码，每张不超过2400万像素。PDF 会转为质量95的 JPEG，沿用 PID 下载尺寸及压缩设置，因此“全部页面”不等于“无损原文件”。想保留更大尺寸可选 original、将压缩阈值设为0，但仍受下载和像素上限限制；动图只取首帧。

已知总页数且完整取得所有页才作为完整作品；缺页、范围请求、到达上限或总页数未知时，文件名带“部分”，消息列出实际收录的原页码及缺页，不能当作全本。已下载图片如果无法解码，整份 PDF 不上传，避免生成静默丢页的文件。

文件发送经过宿主发送队列、限频及 outbox。超时等发送结果未确认时停止，不重传、不回退卡片；请先检查群文件／私聊。协议端必须支持 `upload_group_file` / `upload_private_file`，Docker 须把宿主数据目录挂载到容器相同绝对路径。群文件容量、QQ文件大小限制或协议端不支持私聊文件时仍可能发送失败。

会话中会依次提示“开始处理”“下载完成、排队合成 PDF”“PDF 已生成、正在上传”“处理完成”。下载较久时，每隔至少20秒在取得下一张图片后报告一次已下载数量，不逐张刷屏。图片卡片模式同样有开始、下载和完成提示。提示本身也经过宿主发送队列；任何提示发送未确认都会停止后续下载或外发。

最终总结只显示作品、总张数、文件大小、简短分级与来源链接，不逐项枚举页码。缺页只提示缺少多少张，总页数未知则提示“完整性未确认”；详细缺失页码仍保留在任务记录中，便于定位和指定范围补取。PDF 文件名仍标明实际范围与“部分”，防止把未确认完整性的文件当作全本。

完全未取到图片时，直接提示实际原因：接口 HTTP 500/403/429/404、下载超时或单图超限等，不再统一提示“检查作品分级及页码”。分级拦截仍单独说明。失败原因与状态码保存在任务记录中；接口返回404也不能直接证明原作品已删除。外部接口自身异常时无法保证取得图片，不通过放宽白名单或分级重试。

PID 下载保留原插件的候选地址、尺寸回退和瞬时重试机制。对于图片 GET 的500/502/503/504，按 `pageRetryOnce` 有限重试；404/410、403、429与超限不按这种方式重试。此规则不用于QQ上传或消息发送。`pixiv.re` 等已知图片代理成功返回可信的 `X-Origin-URL` 时，核对官方图片域名、作品号和页号后，将真实路径用于后续页推导，避免每页重复按PID解析。未配置代理时，图片仍通过现有 `i.pixiv.re` 完整路径下载，不使用东京。匿名详情接口拒绝查询与图片入口当前是否可用是两回事，不能保证所有作品永久可取。

PDF 临时数据在 `<数据目录>/pixiv/pdf/job-*`。成功或取消后清理；发送未确认或进程崩溃的残留保留一天，下次 PID PDF 任务清理，不自动重发。关闭功能不会删除配置、分级、历史记录及原插件数据。

能获得页列表时按真实地址、真实页数下载；中间某页失败会记录缺页并继续后面的页，不再因为一个失败页丢掉后续所有页。只有详情但页列表不可用时，从作品图片地址推导页码；没有可靠总页数时做有限探测，停止原因会明确提示，不能把探测结果宣称为全本。

默认一次最多100页，每批最多10张、图片总计4MB、单张下载最多5MB，任务最长300秒。旧实例保留原有 `maxPages`、单图大小等设置（例如原来20页，迁移后仍为20页，可在网页调大）。图片串行处理，不一次缓存整部作品。每批到页数或体积上限就发一张合并卡片，再取下一批；每页标出原始页码，批次不重复首页。

超过每次页数上限时提示下一段指令；可以随时按页范围继续。失败页与达到上限是两回事：前者明确列出缺页，后者提示后续页。未查明总页数时也会标明，不能保证没有未探测到的后续页。

原文件超过下载上限时尝试小尺寸；已有降采样逻辑继续使用系统 ffmpeg（可选）。没有 ffmpeg 或压缩失败时保留原文件；原文件仍受每批体积限制。超过批次大小的单页记为失败并报告，而不是悄悄丢弃。

取消、关闭、权限撤销会停止后续请求与发送；已发页面保留。任何批次发送抛错即按“发送未确认”记录并停止，不再逐张回退或补发，防止重复图片。重启中断任务不自动重跑。卡片展示及平台实际网络可用性仍需QQ现场验收。

## 数据迁移、停用与回滚

原 `plugins.settings.pixiv-illust` 配置复制到顶层 `pixiv`，旧插件从启用名单移除，并被加载器忽略。原插件目录和旧配置保留归档，不能再从插件中心重复启用。

旧 `<数据目录>/plugin-state/pixiv-illust/state.json` 与 `chat-ratings.json` 在首次实际使用内置功能时复制到新目录，不移动、不删除、不覆盖已有新文件。网页在迁移前也能显示原会话覆盖，保存空覆盖后不会复活旧条目。

新数据位于 `<数据目录>/pixiv/`：

- `state/state.json`：已发送作品与死链记录。
- `state/chat-ratings.json`：保留的旧会话覆盖副本；网页保存后使用顶层配置的覆盖。
- `state/tmp/`：下载与压缩临时文件；发送前读取后删除，异常残留在下一任务清理超过15分钟的文件。
- `metadata.json`：最多200件作品的可信分级、标题、作者和页地址缓存；不含 Cookie。
- `ratings.json`：管理员核实的作品分级。
- `history.json`：最多50项任务状态、已发页和缺页，不含图片/base64/Cookie。

关闭功能保留全部数据。新实例从未开启时不会创建数据目录。部署继续使用宿主 `deploy.sh`，保持现有安装、数据路径；不要用旧插件同步脚本更新宿主。回滚应恢复部署前代码及配置备份，原插件目录与状态原件仍在；回滚后不要混用新旧功能同时发送。
